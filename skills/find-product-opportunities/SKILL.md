# 产品机会发现

由 Agent 主导选题、公开研究、反证与最终建议。复用已有信息；只有缺失信息会改变研究方向时才提问。市场不明时先说明暂定范围，可采用技术型独立开发者、低预算、4–6 周 MVP；不要默默替换用户指定的市场、能力或周期。

## 先选择研究深度

- **快速筛选**：用户需要方向或时间有限时，围绕少量差异明显的候选验证最关键的风险，明确哪些结论尚待验证。
- **标准研究**：默认按几批候选逐步收敛，优先把研究预算花在可能改变建议的证据上。
- **深入研究**：用户需要完整市场扫描时扩大覆盖、地域/时间抽样和替代方案比较。

不规定必须生成 20–40 个点子或覆盖固定比例。狭窄行业无需扩成全行业研究。当新增搜索只重复已有证据、无法改变选择或下一步实验时停止；证据不足但仍有可区分的假设时交付“待验证”。

## 发现与筛选

先读取 [证据规范](references/evidence.md)。从持续发生的任务与近期变化两方面寻找切口：谁在什么情境下要完成什么事，现有办法付出什么成本，谁承担责任或付款，为什么现在值得改进。

需要拓展方向时读取 [发现方法](references/discovery-playbook.md)，再按相关主题查 [模式库](references/opportunity-pattern-library.md)；来源受阻时读取 [来源策略](references/source-strategy.md)。[BuilderPulse 研究](references/builderpulse-study.md) 仅用于维护方法和理解历史样本。

每个有潜力的候选应能说明：目标用户与任务、当前替代、付款人、最小价值切口、首个可达渠道、最可能推翻它的解释。早期不要求为每个点子填写完整卡片。

检查长期付费任务、手工流程和迁移/审核/导出等稳定需求，也检查成本、能力、规则或分发变化。痛点可能来自配置、文档或定价；开源增长可能产生支持、集成、验证等相邻需求。不要把抱怨或 stars 直接转成完整 SaaS 替代品。

## 验证关键主张

对强候选核查需求行为、支出/责任、竞争替代和分发可达性。正式推荐需要至少三类独立的支持信号及一次可追溯反证检查。不同页面转述同一新闻不算独立证据；背景信息和反对证据不能填充支持门槛。

主动检查免费/原生方案、脚本和人工服务，关注迁移成本、平台依赖、获客门槛、实际开发与运营成本。Google Trends 只表示相对兴趣；搜索摘要、聚合日报和模型推断只能帮助发现来源。缺少登录或付费数据时继续公开研究，标明结论限制。

## 裁决

先看致命约束，再比较价值、证据、交付和分发。候选少时用理由清晰的对比即可；需要量化排序或保存标准工件时读取 [评分规范](references/scoring.md)。分数不代表市场成功概率，不用 1–2 分的细差替代判断。

- **recommendation**：1–3 个达到门槛的 finalist，恰好一个主推荐。仅有一个好机会时直接推荐一个。
- **needs-validation**：关键证据缺失或冲突，保留待验证假设及最低成本的判别实验，不伪装成已验证推荐。
- **no-go**：在当前约束下已发现明确否决理由，说明哪些条件改变后值得重开。

## 交付

按 [报告规范](references/report.md) 给出结论、关键比较、证据与反证、风险及下一步验证。默认在对话中交付。实验围绕最不确定且最致命的假设设计，给出可观察输出、投入上限和停止条件；时间随实际渠道和购买周期确定。

研究授权不自动包含开发、注册、付费、联系或发布。用户已经明确要求的下一步在该范围内继续，不重复索要授权。需要保存时，在用户指定的私有目录使用 [模板](assets/report-template.md)，从本技能目录运行：

```bash
python scripts/opportunity_radar init --output <path>
python scripts/opportunity_radar score --run <path>
python scripts/opportunity_radar validate --run <path>
```

保存工件交付前通过校验；校验只证明结构和引用一致，证据独立性与商业判断仍需审查。私有研究数据不得进入公开插件仓库。
