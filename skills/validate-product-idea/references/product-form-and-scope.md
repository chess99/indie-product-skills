# 形态与首版取舍

只比较会改变当前决策的形态。先使用用户已经确定的平台、技术能力与分发条件；不要求遍历所有选项。

## 让形态匹配任务

| 任务约束或使用位置 | 可优先检查的形态 | 需要核实的代价 |
|---|---|---|
| 链接即可访问、协作或频繁集中更新 | Web / SaaS | 联网、托管、数据存储与浏览器能力限制 |
| 随身使用、相机与位置等设备能力 | 移动应用 | 系统权限、后台限制、商店规则与多系统维护 |
| 本地文件、离线、设备算力或系统集成 | 桌面软件 | 安装信任、签名、更新和跨系统支持 |
| 操作发生在浏览器页面或现有宿主中 | 扩展 / 插件 | 宿主 API、权限、审核与平台变化 |
| 开发者重复操作、管道与批处理 | CLI | 安装与环境兼容、错误反馈、升级与分发 |
| 功能需嵌入其他软件、自动化调用 | API / SDK | 接入成本、鉴权、可靠性与按量服务成本 |

这些是取舍线索，不能仅凭某一特征决定平台。混合方案会增加同步、支持和发布成本，只有核心任务确实跨端时才纳入首版。核查实际平台 API 与规则后再承诺能力。

分开讨论产品交付和获客入口：桌面应用可以有营销网站，API 可以靠文档获客；官网的存在不决定产品必须做成 Web。产品形态也不决定收费方式，根据价值发生频率、边际成本和购买习惯比较买断、订阅、按量等方式。

## 确定最小完整价值路径

先描述一个目标用户能独立完成的具体结果，再从结果倒推必要功能。每个候选功能检查：缺少它是否无法完成任务、是否无法验证关键假设、是否存在不可接受的交付风险。必要的错误恢复、数据保护与权限处理属于可用闭环，不能为缩小范围一律删除。

将研究实验、技术验证和首版产品分开：手工出报告可验证结果价值，本地脚本可验证处理能力；它们都不自动证明自助安装、使用、付费和维护链路成立。

交付适量的范围说明即可：

- 一个核心用户任务与支持环境。
- 首版必须完成的输入、处理、结果与失败路径，以及可观察的验收条件。
- 暂缓功能与重新纳入的触发条件。
- 最危险的未知与先行实验；依赖外部审核或接口时标明尚未验证的条件。

例如，只在本机处理文件且没有协作需求的工具，首版可以不引入账号和云同步；仍需验证文件格式、输出正确性、错误恢复，以及目标环境中的运行方式。是否需要图形界面取决于使用者和任务，不能仅按开发便利选择 CLI。
