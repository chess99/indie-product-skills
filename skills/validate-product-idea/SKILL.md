# 产品想法验证

围绕用户已有想法做投入决策。复用用户任务、目标人群、已有证据、平台选择、预算与时间限制；只询问会改变判断的缺失信息。用户只问形态或首版范围时，聚焦该决策，不要求重新完成市场研究。

## 找到需要验证的假设

把想法还原为具体任务：谁在什么时刻遇到什么问题，现在如何完成，为什么愿意改变，谁付出时间或金钱。将需求、触达、付款、交付可行性中的已知事实与待验证假设分开；优先处理失败后会使当前方案失去价值的假设。

主动检查免费的原生能力、现有软件、手工服务和脚本，比较切换、安装、权限与学习成本。投诉、点赞、搜索量和“愿意试试”不能直接证明购买；缺少数据也不等于没有需求。引用保留来源、时间、受众与观察范围，同源转载按一个原始来源理解。

Agent 先完成可做的公开研究与现有材料分析。需要深入分析访谈或评论时可使用 `customer-research`，定价专项可使用 `pricing`；不把购买工具、拉取导出或自行研究变成用户开始任务的条件。

## 选择形态与首版范围

形态未定或需要裁剪 MVP 时，读取 [形态与首版取舍](references/product-form-and-scope.md)。比较与任务有关的少数可行方案，从设备能力、使用位置、数据与离线限制、分发、收费和持续维护做取舍。保留用户指定的平台；发现硬约束冲突时解释具体冲突和备选，不静默替换需求。

首版围绕一条完整价值路径定义：输入或触发、核心操作、可用结果、失败处理。给出能观察的完成标准与暂缓项。营销网站、账号、云同步、订阅和多端支持都需要具体理由；验证原型可以比首版更小，但不能冒充已可交付产品。

## 设计并判断最小实验

针对最致命的未知设计能区分解释的实验。说明目标受众、招募渠道、观察行为、投入上限，以及继续、调整、停止的判据；阈值需结合渠道、成本与购买周期解释，不统一规定样本数、天数或转化率。

- 验证问题是否存在：查近期实际任务、现有支出和反复绕行的行为。
- 验证方案是否有效：用原型、手工服务或最小工具观察任务完成、结果质量和再次使用。
- 验证是否愿意付费：在明确价格与交付条件下观察有成本的承诺，区分兴趣、意向、实际付款和复购。
- 验证能否交付：只验证最关键的平台能力、接口、权限或性能约束。官方规则按当前来源核对，技术演示成功不能代替需求证据。

未执行的实验写成计划，不编造访谈、购买或转化数据。实验失败时检查受众、渠道触达和测量是否有效，再判断它否定了哪个假设。公开研究可支持初步投入建议；无法验证的真实采用与付款行为明确保留为缺口。

## 交付与边界

先给当前投入建议：继续到下一项有限投入、调整假设或暂缓/停止，并说明证据与反证。按任务补充推荐形态、首版边界、关键未知和下一项实验；不要将“值得做小实验”写成“已经验证市场”。证据不足时给出待验证结论，不靠精细分数制造确定性。

沿用已有授权完成可做的研究、原型或本地检查。尚未授权的联系用户、投广告、收费、注册或发布，先准备可审阅的具体内容再请求授权。默认在对话中交付；只在用户要求保存时写入其指定的私有目录。
